OSTree (ASan build): feeding a crafted repository configuration keyfile into the routine that writes a repo's config triggers a one-byte heap out-of-bounds READ deep inside glib's bundled PCRE 8.37 regular-expression engine. The write-config path first enumerates the config's group names; glib hands back each group name as its own tight heap allocation, produced by duplicating the parsed string with no trailing guard byte (in the crashing case a 10-byte buffer holding exactly the group-name bytes). For every group, OSTree decides whether that group is a remote definition by matching the group name against a compiled regular expression through glib's GRegex wrapper. During that match the underlying PCRE engine performs newline detection: at a point where the scan cursor has advanced to the position immediately after the final character of the subject, its newline-checking helper dereferences the byte at that cursor to classify whether it sits on a line boundary. Because the subject string is exactly its own length with no readable byte past the terminator region the sanitizer poisons, this dereference lands one byte to the right of the end of the group-name allocation. The direction is a read (not a write) of a single byte, one position past the high end of the heap-allocated group-name buffer, at the end-of-subject cursor used by the regex matcher. The root cause is in the third-party PCRE 8.37 matching code (an over-read past the end of the subject during newline classification), reached here through OSTree's regex-based detection of remote-configuration groups rather than through any bounds error in OSTree's own arithmetic.

Fix note: the recorded fix commit and its touched files are unrelated to this crash path. Those changes introduce a new in-place kernel-argument editing API and its plumbing (deployment/sysroot boot-config handling), which has no connection to config-keyfile parsing, GRegex/PCRE matching, or the group-name allocation involved here; the reported crash-vs-fix file overlap is zero. The genuine remedy would live in the regex engine's newline/end-of-subject handling (or in avoiding an unguarded match against a non-padded subject), not in the deployment code the commit modifies, so fix_commit may be wrong.
