This is a 1-byte heap-buffer-overflow WRITE, found by the fmt library's `chrono-duration` fuzz target (feeding pseudo-random format strings and floating-point values into `fmt::format_to` for a `std::chrono::duration<long double, ...>`).

Mechanism:

fmt's floating-point writer formats a decimal value into a fixed decimal-string representation (integer part + optional fractional zeros) and, before doing any writing, first computes the total number of output bytes the result will need. It then grows/resizes the destination `memory_buffer` to exactly that computed size and hands back an output iterator that writes into the freshly reserved region.

The size computation has a corner case around the "always show a decimal point" mode (equivalent to printf's `#` flag / `showpoint`), which is used here because the duration's fractional-seconds formatting requests a decimal point even when there will be zero digits after it (e.g. producing something like "N." rather than "N"). The pre-fix logic only added the one byte for the decimal-point character itself when it had *also* decided to pad the fraction with at least one zero digit; when the chosen output style already fixed the number of trailing zero digits at 0 (the "fixed" formatting style, which does not fall back to forcing at least one zero digit the way the general style does), that zero-digit condition was false, so the branch that reserves the extra byte for the point was skipped entirely — even though the point character itself is still emitted a few lines later regardless of how many fractional digits follow it.

The result is that the computed `size` undercounts the real output by exactly one byte in this style/precision combination. The buffer is allocated/resized to that undercounted size (985 bytes in this run), and then the actual character-writing pass, which is driven by the true field layout rather than by the (wrong) reserved size, writes the decimal-point byte one past the end of the just-allocated 985-byte block. ASan reports this as a 1-byte WRITE heap-buffer-overflow immediately to the right of the allocation. Nothing is read out of bounds; only the buffer-growth/size bookkeeping for the write path is affected, and only the single trailing byte overruns.

So: direction = buffer under-allocated then overrun on write (grow-side accounting bug), effect = 1-byte OOB WRITE past the end of the heap-allocated formatting buffer; the affected quantity is the precomputed total-size counter used to size the buffer before the digits/point/zeros are actually emitted.

Patch:

The fix touches the same size-computation block: it now unconditionally accounts for the decimal-point character whenever "always show point" mode is active (adding it up front, independent of how many trailing zero digits will follow), and removes the extra "+1" that used to be bundled into the zero-digit branch (since the point is now already counted separately). This makes the reserved size match the real output in every combination of style/precision, closing the off-by-one and eliminating the overflow.

fix_commit judgment: the fix commit's file (`fix_files`) and the patch content shown directly modify the exact size-accounting logic inside the exact floating-point-writing helper function that ASan's stack trace names as the crashing frame and as the top allocation frame for the overflowing buffer — the same helper is reached from the same duration-formatting call chain seen in the crash. The patch's semantic change (always reserving one byte for the decimal point instead of only doing so when trailing zero digits are also being reserved) is precisely the missing accounting that explains a 1-byte-short buffer under `showpoint`/fixed-style formatting. This is a strong, direct match — the fix_commit looks correct for this crash.
