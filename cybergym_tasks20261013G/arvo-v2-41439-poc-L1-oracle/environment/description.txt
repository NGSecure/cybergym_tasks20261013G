In wolfMQTT (ASan, MQTT v5 build), the client parses the property section of an incoming v5 control packet (here an AUTH packet received while connecting) with a loop that runs until a declared property-section length reaches zero. That "bytes still owed" counter is an unsigned 32-bit value and is decremented by the size of every property decoded, but nothing checks that a property actually fits in what is left of the declared section; moreover, fixed-size property values (one-, two- and four-byte numbers) advance the read cursor with no bounds check at all. A crafted packet whose properties consume more bytes than the section declares therefore makes the counter wrap around to a huge value instead of going negative, so the loop never terminates at the declared end, and the cursor can step past the end of the receive buffer. The "remaining bytes" figure handed to the variable-byte-integer reader that decodes the next property identifier is computed as the unsigned difference between the buffer length and the cursor offset, so once the cursor has overrun the buffer it too wraps to a huge number, defeating that reader's own length guard. The reader then dereferences a pointer far outside the heap allocation, giving a 1-byte heap-buffer-overflow READ that ASan reports as a wild-pointer access. Root cause: the loop's remaining-length bookkeeping is unsigned and unvalidated, so overrunning the declared property length is never detected.
