fmt (v8, ASan build): formatting a single `long double` argument whose value forces the exact/shortest-round-trip decimal path drives fmt into its Dragon-style floating-point conversion, which performs arbitrary-precision arithmetic using several `bigint` scratch values (numerator, denominator, and two bounds). Each `bigint` is backed by a small-buffer-optimized `basic_memory_buffer<uint32_t, 32>` that keeps a 32-element (128-byte) inline array living directly in the caller's stack frame and only heap-allocates once it needs to hold more than 32 limbs. During the conversion the code scales one of these values by a power of ten, which repeatedly squares an intermediate `bigint`; squaring first moves/reassigns the buffer and then grows it to hold the doubled limb count.

Root cause: the buffer's move handling is buggy for the small-buffer (inline-storage) case. When a source buffer is still using its inline array, the move copies the inline limbs into the destination and resets the source's data pointer and capacity back to its own inline store, but it never resets the source's logical element count. The moved-from buffer is therefore left in an inconsistent state: it points at (an empty) inline capacity yet still reports the old, non-zero size. When that same moved-from buffer is later reused and asked to grow, the growth routine allocates the larger backing store and then copies `size()` existing elements from the old (inline, stack-resident) storage into the new one via an uninitialized copy. Because the reported size is stale and larger than the number of limbs actually present in the inline array, the copy loop walks one 4-byte limb past the end of the inline array.

Direction: this is a 4-byte READ overflow that occurs while the buffer is being grown (capacity increasing). The offending quantity is the buffer's element-count field, which is not cleared on move; the over-copy reads just past the inline limb array embedded in the Dragon routine's stack frame (the `numerator` scratch value), which is why AddressSanitizer reports a stack-buffer-overflow read of size 4 in the copy performed by the buffer's grow step. The fix is to reset the moved-from buffer's size to zero as part of the inline-storage move, so a buffer that has been moved from reports a size of zero and a subsequent grow copies nothing stale.
