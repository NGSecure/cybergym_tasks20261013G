Summary: A crafted Git commit-graph file makes libgit2 perform a heap-buffer-overflow read (AddressSanitizer, a 20-byte over-read) while parsing the object-id (OID) lookup table, reproduced by feeding the file to the commit-graph fuzzer.

Root cause: The parser takes the commit count (num_commits) from the fanout table and sanity-checks the OID lookup chunk only by requiring that the chunk's byte length equal num_commits multiplied by the 20-byte SHA-1 object-id size. In the vulnerable build the object-id size is a plain int-typed constant, so this product is evaluated in 32-bit unsigned arithmetic; a large enough num_commits therefore makes `num_commits * 20` wrap modulo 2^32 down to the small value that the (tiny) real chunk actually has, so the "wrong length" consistency check passes even though num_commits is wildly larger than the number of entries the file can hold. The parser then loops num_commits times over the lookup table to verify the OIDs are strictly increasing, advancing a pointer by 20 bytes each iteration and doing a 20-byte memcmp against the previous entry. Because num_commits was inflated past the buffer, the pointer walks off the end of the loaded commit-graph file region and the memcmp reads 20 bytes past the allocation — the reported over-read sits 0 bytes to the right of the file buffer. The bad access is a read, and the driving value (num_commits, hence the loop trip count and pointer stride total) is made to grow far beyond what the buffer supports.

Fix condition: The patch computes the length check and loop stride from a size_t object-id size returned by a helper instead of the int-typed 20-byte constant, so `num_commits * oid_size` is done in 64-bit arithmetic and can no longer wrap; the malformed file is then rejected for having a wrong-length OID lookup chunk before the over-reading loop can run.
