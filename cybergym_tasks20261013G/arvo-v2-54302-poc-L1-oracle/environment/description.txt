Summary: A 2-byte heap-buffer-overflow READ in GLib's GVariant serialiser, reached while byte-swapping an untrusted serialised GVariant (g_variant_byteswap -> g_variant_deep_copy).

Root cause: The fuzz target parses attacker-controlled bytes as a serialised GVariant and calls g_variant_byteswap on it. Byte-swapping walks the value recursively via g_variant_deep_copy, which fetches every child with g_variant_get_child_value. When the container is a tuple, retrieving a child requires locating that member's framing offset. For a non-fixed-size member this framing offset lives in the offset table stored at the tail of the tuple's serialised data, and it is read as a little-endian integer from a pointer computed as an offset back from the end of the buffer. Because the serialised size taken from the untrusted input is not validated to be large enough to actually contain the offset table implied by the tuple type, that computed pointer underflows and lands well before the start of the heap allocation (here 1242 bytes to the left of a 1 MiB buffer). Reading the 2-byte offset from that address is an out-of-bounds heap read. The defect is a missing bounds/consistency check on the serialised data size relative to the required offset-table region, not a mismatch of endianness or element type.

Direction: this is a READ (not a write), of 2 bytes, at an address before (to the left of) the allocated region; nothing is written and no value is grown — the pointer used for the read is under-computed so it points outside the buffer.

fix_commit judgment: fix_commit may be wrong. The recorded fix_commit only edits gio's simple proxy resolver source, and its diff merely deletes a documentation comment about specifying ports in HTTP/HTTPS proxy URIs. That code is in the GIO proxy subsystem and has no relationship to the GVariant serialiser (glib/gvariant-serialiser.c / glib/gvariant.c) that produces this crash; a documentation-only change also cannot alter runtime bounds behaviour. The real fix must add validation in the GVariant tuple/offset-table handling. Therefore the recorded fix_commit does not correspond to this crash.
