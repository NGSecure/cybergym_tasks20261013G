net-snmp's AgentX packet parser copies a PDU's community string into the context-name field using a C string duplication, but records the context-name length from the separately stored community length rather than from the duplicated string. The community field is length-delimited binary data and can contain embedded NUL bytes, so the duplicated buffer ends up shorter than the recorded length. Nothing checks that the two agree. Later, when the same PDU is re-encoded as an SNMPv3 message, the scoped-PDU header builder copies exactly the recorded number of context-name bytes out of the short heap allocation, producing a heap out-of-bounds read of a few bytes past its end. The root cause is a length/content mismatch: a string-terminator-based copy is trusted to be as long as a separately tracked byte count.
