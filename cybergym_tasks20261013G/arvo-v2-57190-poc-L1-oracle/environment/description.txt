curl's RTSP protocol handler processes interleaved RTP media data that a server can multiplex onto the same connection as RTSP control replies, exercised here through curl's own RTSP fuzz target under AddressSanitizer. Because a single socket read can catch an RTP-over-RTSP packet in the middle, the handler keeps per-connection state remembering how many bytes of an incomplete packet were held over from the previous read; on the next read it merges that carried-over amount with the freshly read chunk before continuing to walk the merged data looking for a complete packet. Once that walk finishes, the code needs to know how much of the just-received chunk was actually consumed versus how much data is still outstanding, so it subtracts the amount still outstanding from the number of bytes read on this particular call, and uses that difference to reposition a pointer that is supposed to track progress inside the fixed-size per-transfer receive buffer for this connection. That subtraction silently assumes the outstanding amount can never exceed what was freshly read in the current call — but the outstanding amount is actually computed from the combined old-carryover-plus-new-data total, so it can legitimately still include bytes that arrived in an earlier call. When the amount still outstanding exceeds the freshly-read byte count, the subtraction produces a large negative-going offset and the tracking pointer is walked backwards past the very start of the receive buffer. Code immediately afterward performs a one-byte equality check between that pointer and the merged-data pointer to confirm the two stayed in sync, and dereferencing the now out-of-bounds pointer for that check is what AddressSanitizer flags as a heap-buffer-overflow read, landing just a couple of bytes before the start of the receive buffer's heap allocation rather than past its end.

The fix replaces the whole leftover/carry-over storage mechanism for this state: instead of using a general-purpose growable string-buffer abstraction (with an implicit NUL terminator and an overall size cap configured once when the connection is set up) to hold the bytes carried over between reads, the handler goes back to owning a plain heap block for that purpose, directly allocating and growing it with explicit reallocation and tracking its length in its own dedicated field; every path that used to reset or free the growable buffer — successful full drain, a write-callback error, and connection teardown — is updated to manage that plain block instead. This removes the abstraction whose own bookkeeping around merged/reset data spanning two separate reads was implicated in producing the mismatched outstanding-vs-freshly-read accounting that led to the out-of-bounds pointer walk.
