lwan's HTTP/2 header-compression (HPACK) Huffman decoder, exercised through its dedicated fuzz entry point, ASan build: incoming Huffman-coded bytes are processed through a small bit-level reader that keeps two counters — how many bits are currently buffered for the decoder to inspect, and how many bits of the whole input still remain unprocessed overall. Whenever the buffered bits run low, the reader tops itself back up by loading a multi-byte, big-endian chunk directly from the input buffer at the current byte offset, so it always has a wide enough lookahead window to recognize the next Huffman code. After each group of bits is handled, a helper decides whether the reader should be treated as exhausted, purely by checking whether subtracting the just-handled bit count from the "bits still remaining overall" counter would drive it negative; only that underflow case is treated as "no more input." The case where the subtraction lands exactly on zero — meaning the input has just been fully used up, with nothing left — was not treated as exhausted, so the decoder is told it may keep going. On the fuzzer's crashing input, the very last valid bits happened to drain the remaining-bits counter exactly to zero, so the decode loop performed one further top-up load of its multi-byte lookahead window starting right at the end of a 6-byte input allocation. That speculative load reads a fixed-width chunk larger than the bytes actually left in the buffer, walking a few bytes past the end of the heap allocation before the read completes — an 8-byte read that overruns the 6-byte buffer by several bytes, i.e. a heap out-of-bounds READ, not a write, and the overrun grows forward past the end of the allocated region rather than shrinking any buffer.

The upstream fix changes that exhaustion check so it also reports "no more input" the moment the remaining-bits counter reaches exactly zero (in addition to the pre-existing underflow case), so the decode loop stops requesting another lookahead refill as soon as all bits have genuinely been used up instead of performing one extra out-of-bounds top-up. Because a second, independent copy of the very same counter-and-exhaustion logic exists in a code-generation template used to (re)produce the decoder's lookup tables, the same corrected boundary condition is mirrored there too, so any future regeneration of those tables keeps the same fix rather than reintroducing the bug. A minimized reproducer for the original failure is also checked in as a stored regression case for the fuzz target. This patch and its target file/function line up exactly with the reported crash's call path and the counter it manipulates, and the upstream fix metadata for this report points at the same commit, so the recorded fix commit looks correct — no "fix_commit may be wrong" concern here.
