One-sentence summary: In ClamAV's PDF parser (ASan build), scanning a PDF containing an encrypted string object whose declared content length is zero triggers a 1-byte heap-buffer-overflow READ.

Crash mechanism:
- While ClamAV assembles the parsed representation of a scanned PDF's objects (the path invoked from cli_pdf via pdf_export_json, through the routine that finalizes a decoded/decrypted string for output), a small helper strips an optional leading '<' and trailing '>' delimiter pair from the raw string bytes before any further hex/decrypt processing.
- This helper takes the string's start pointer and its reported byte length, and computes the position just past the declared end by adding the length to the start pointer. It then unconditionally inspects the byte immediately *before* that computed end position to decide whether it is a closing '>' that should be stripped.
- Nothing checks beforehand that the declared length is at least 1. For a PDF string object with a declared length of 0 (e.g. an empty encrypted string), the computed "end" pointer is identical to the start pointer of the buffer holding the string bytes -- a buffer freshly allocated (via cli_calloc) to hold exactly that (empty) string. Reading "the byte before end" in that case reads the byte immediately preceding the very first byte of that allocation: a 1-byte-to-the-left heap-buffer-overflow read, matching the ASan report's "1 bytes to the left of [a] 1-byte region."
- Call chain matches the report exactly (cli_pdf -> pdf_export_json -> the string-finalization routine -> the delimiter-stripping helper), and it is reached through ClamAV's ordinary decryptable-PDF handling path, not through any fuzz-only harness code.

Fix verification: fix_commit 82491dabaa9e2d6004519371b67dd36aa4dec3c9 adds exactly the missing guard: before any of the start/end pointer arithmetic runs, the routine now checks whether the declared length is less than 2 and, if so, returns immediately without touching the buffer. Requiring at least 2 (not just a non-zero length) also closes a related degenerate case: with a declared length of exactly 1, treating that single byte as both the candidate leading '<' and the candidate trailing '>' would leave the routine with a start pointer that has advanced past its end pointer, an unsafe state for the hex-decoding logic that follows. This matches crash.json's recorded fix_files (the single file the diff touches is exactly the crash file), and is independently corroborated by meta.json, whose own "fix" commit URL carries the identical hash -- two independently populated records agreeing on the same commit is strong evidence this is the correct, non-mismatched fix. fix_commit is confirmed correct as recorded; no correction needed.

Direction: this is a READ (not a write), and the out-of-bounds access is an underflow -- one byte before the start of the buffer (left of the allocation), not an overrun past its end. It is triggered by driving the PDF string object's declared length down to zero (a degenerate/shrunk-to-empty length value), not by growing any buffer, index, or counter.
