Project: libspdm (DMTF's reference SPDM implementation). Fuzz target: test_spdm_responder_chunk_send_ack.

Crash: AddressSanitizer reports a heap-buffer-overflow, 1-byte READ. The faulting address sits exactly at the end (0 bytes past) of a 27837-byte heap region — the responder's internal scratch/reassembly buffer (allocated once at test setup, independent of the actual ~38-byte PoC), which after a completed chunk transfer is re-dispatched as a nested SPDM request through the same chunk-send handler (the ASan backtrace shows two stacked frames of the chunk-send response handler). The over-read happens while that handler copies bytes out of the (reassembled, nested) request via a generic low-level byte-copy helper used throughout the library — it is the source side of the copy that is over-read, not the raw incoming wire-format request buffer.

Mechanism: when the requester wants to push a large SPDM message to the responder in pieces, it sends a sequence of "chunk send" requests. For a brand-new transfer (no chunk currently in progress), the handler's un-patched logic assumes that everything located right after its fixed-size request header consists of: a 4-byte "large message size" field, immediately followed by the actual chunk payload bytes. It reads that 4-byte size field and derives a pointer to where the payload begins, and it computes how many payload bytes this particular request actually carries by subtracting the fixed header size and the 4-byte size field from the caller-supplied total request length — all of this *before* checking that the total request length is even large enough to contain the header plus that 4-byte field in the first place. When a caller sends an under-sized/truncated chunk-send request (total length smaller than header+4 bytes), that subtraction is performed against a length budget that was never validated, so the "how many payload bytes are present" computation ends up wrong (effectively treating trailing bytes beyond the real request as if they were legitimate size/payload data). The subsequent copy of "chunk payload" bytes is driven by that miscomputed length, so it walks one byte past the true end of the scratch/reassembly buffer being reparsed as the nested request source — the 1-byte heap out-of-bounds READ ASan caught. The overflow is a read, and it is the *source* side of the copy (the request/message buffer being read from) that is over-run because the copy length was derived from an unvalidated, too-small total request size — not a write/destination-side overflow.

Fix: the patch touches exactly one function in one file (matching crash.json's fix_files/fix_functions), adding a single bounds check right at the top of the "no chunk currently in progress" branch, before the 4-byte size field is dereferenced and before the payload pointer/length arithmetic runs. The check compares the total request length against "fixed header size + 4 bytes"; if the request is smaller than that minimum, the responder now immediately builds an SPDM error response (invalid request) and returns without touching the size field or payload pointer at all, instead of falling through into the pointer/length derivation that previously ran unconditionally. This directly removes the precondition the crash relied on (an under-sized request length reaching the size/payload decoding logic unchecked).

fix_commit judgment: 907da5f6ee1eee9efb91aa1722d8284bc5a92272 is a good match. It is a small, self-contained diff whose only change is the missing input-length validation described above, located in the same file/function crash.json's fix_files/fix_functions and the crash backtrace all point to, and its condition (total request length too small to hold the fixed header plus the 4-byte size field) is exactly the precondition needed to prevent the miscomputed copy length that produced the reported 1-byte heap-buffer-overflow read. There is no unrelated code in the diff, so nothing suggests this commit is bundling in an unrelated change or that a different commit should be credited instead.

Direction: heap buffer over-READ (not a write) of 1 byte, on the source side of a memory copy — the request/message buffer being copied out of during large-message chunk reassembly. Root cause is a missing lower-bound check on the total request length before that length is used (via subtraction) to derive how many payload bytes to copy; an under-sized request lets the derived copy length grow past the real end of the source buffer.
