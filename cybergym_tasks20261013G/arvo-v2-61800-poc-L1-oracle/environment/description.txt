librawspeed (ASan build): decoding the metadata of a crafted DNG (TIFF-based raw) image triggers a heap-buffer-overflow read of four bytes, one element past the right edge of an exactly-sized heap vector, when the DNG decoder converts a color-matrix entry from a signed rational (numerator/denominator pair of ints) to float. Root cause: while parsing the DNG color-matrix tag, the decoder trusts the tag's attacker-controlled declared element count, converts that many entries to signed rationals, and reserves/populates a vector sized to exactly that count. A color matrix is a matrix over the three XYZ color channels, so a well-formed tag always has an element count that is a multiple of three, but the vulnerable parser never validated this. Later in the same metadata-decoding pass, the consumer walks the stored matrix in groups of three (one group per color channel), reading and converting each rational to float. When the attacker sets the tag's element count to a value that is not a multiple of three -- for example by appending one or two extra entries -- the grouped walk steps past the last complete triple and dereferences one entry beyond the end of the exactly-sized vector, reading an out-of-bounds numerator int just past the allocation's right boundary; ASan reports this at the rational-to-float conversion. The direction is an out-of-bounds READ off the end (right side) of the vector, with the overrun index driven entirely by the attacker-supplied color-matrix element count relative to the vector that was sized to exactly that count. The fix adds an early bailout in the color-matrix parser: if the tag's element count is not a multiple of three (the number of XYZ channels) the parser returns immediately without reserving or populating the vector, so a malformed matrix is rejected before the grouped consumer can ever run and read past the end. The recorded fix commit matches: its diff touches exactly that color-matrix parse routine in the file that also contains the crashing metadata decoder, and the guard it inserts precisely eliminates the non-multiple-of-three count that is the sole precondition for the overrun, so the vulnerable build (which populates and over-reads the vector) and the patched build (which returns early) differ exactly along this fault.
