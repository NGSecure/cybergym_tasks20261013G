Summary: A crafted image whose embedded ICC color profile is queried for a tag that is absent from the profile's tag directory triggers a negative-index (index -1) out-of-bounds array read in Little-CMS, reported by UndefinedBehaviorSanitizer while ImageMagick fetches the profile's textual description.

Root cause: The vulnerability is reached through the profile-info path (ImageMagick's GetICCProperty -> cmsGetProfileInfoASCII -> GetInfo), which asks Little-CMS to read a specific tag from the parsed ICC profile. Internally the tag lookup helper (_cmsSearchTag) returns -1 when the requested tag signature is not present in the profile. In the vulnerable build, the "not found" branch jumps to the function's shared error/cleanup label, and that label unconditionally evaluates the per-tag pointer array using the lookup result as the subscript (Icc->TagPtrs[n] with n == -1). Because the array is a fixed 100-element table of pointers, reading element -1 is an out-of-bounds access below the start of the array — an undefined-behavior read, not a write, caused by the index shrinking to a negative value rather than by any oversized/growing value.

Fix relationship: fix_commit 1c3ccf4724333743dbef6d828bb22fc7776ad1e8 matches this crash. The patch changes the "tag not found" branch so that instead of jumping to the shared cleanup label (which dereferences the pointer table at the -1 index), it releases the mutex and returns NULL immediately, before the negative index is ever used as a subscript. This precisely addresses the reported condition: the remaining jumps to the cleanup label all occur only after the lookup index has been confirmed to be a valid (non-negative) tag slot, so the out-of-bounds read can no longer happen for the missing-tag case.
