Summary: A crafted JPEG-2000 image triggers an 8-byte heap out-of-bounds read in JasPer's JPC tile-decoding stage while GraphicsMagick's JP2 coder is decoding the file.

Root cause: When decoding the codestream, JasPer first initializes each tile and allocates a per-component sample matrix (a 2-D sequence buffer) sized from the tile/component geometry declared in the codestream headers (allocation path: jas_seq2d_create -> jas_matrix_create -> jas_malloc during tile initialization). In this crash the allocated region is 42036 bytes. Later, during the tile-decode pass in src/libjasper/jpc/jpc_dec.c, the decoder walks the component sample data and reads 8 bytes located just 3 bytes past the end of that matrix buffer. The overflow is a READ past the end of the allocation (not a write), and it happens because the extent used to index the sample data during tile decoding does not match the smaller extent that was used to size the matrix at initialization time. The input is malformed (the decoder emits a "trailing garbage in marker segment" warning), so inconsistent geometry / marker-segment values in the codestream let the decode loop step beyond the bounds established at allocation.

Fix-commit note: fix_commit may be wrong. The recorded fix_commit (971c7d48...) and every entry in fix_files/fix_functions touch only the project's compilation tooling and CMake configuration (adding a C++ language standard, pthread library detection/linking, and diagnostic output) — none of them modify the JPEG-2000 decoder or the crash file src/libjasper/jpc/jpc_dec.c where the out-of-bounds read occurs. This is consistent with fix_crash_overlap=0: the associated commit is a compilation/toolchain change and does not add any bounds/geometry check that would prevent this overflow, so the true corrective commit for this crash is elsewhere.
