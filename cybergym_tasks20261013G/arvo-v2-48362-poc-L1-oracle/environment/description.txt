Summary: A one-byte heap out-of-bounds READ in libcoap's URI/proxy-URI parsing helper, triggered when the parser is handed a zero-length URI string.

Root cause: The internal URI splitting routine (reached from coap_split_proxy_uri via coap_get_uri_path while handling a CoAP Proxy-Uri option) validates only that the input string pointer and the output URI struct are non-NULL, but it does not check the input length before it begins scanning. It immediately dereferences the first character of the string (the scheme-detection test `if (*p == '/')`, with p pointing at the start of the input) without first confirming that at least one byte is present. When the supplied length is zero, the string pointer points exactly one byte past the end of the 262-byte heap buffer that backs the parsed PDU (allocated in coap_pdu_init), so reading `*p` accesses one byte to the right of the allocation. AddressSanitizer reports this as a 1-byte heap-buffer-overflow READ at offset 0 (immediately past the region). The read never writes, and the out-of-bounds pointer is at the buffer's upper boundary rather than growing past it in a loop — it is a single missing length precondition, not an index that increments too far.

Fix: The fix strengthens the entry guard from `if (!str_var || !uri)` to `if (!str_var || !uri || len == 0) return -1;`, so a zero-length input is rejected before the first-character dereference. This directly addresses the crash condition (len == 0 leading to a read of the first byte of an empty string).

fix_commit judgment: The recorded fix_commit (see crash.json) matches the crash. The patch modifies the same helper's opening validation, adding the `len == 0` clause to the exact guard that precedes the crashing dereference; this is the specific variable (len) and check whose absence caused the one-byte over-read.
