lwan's text-template engine, exercised through its dedicated template-compilation fuzz entry point (ASan build): the harness compiles an attacker-supplied template string against a fixed, compile-time table of variable descriptors. Each descriptor is a small struct that records a variable's name, its byte offset inside the backing data structure, and — depending on the variable's kind — one of several mutually exclusive behavior payloads: a plain or escaped string variable carries a pair of accessor function pointers, a sequence/list variable carries a generator coroutine together with a pointer to the child descriptor table used when iterating that list's items, and a lambda variable carries a single formatting callback. In the vulnerable build all of these per-kind payloads were packed into one anonymous union, and critically the child-descriptor-table pointer (the "list descriptor") lived inside that union, sharing the same storage bytes with the string variable's second accessor function pointer and with the lambda callback. When the template parser encounters a section opener of the form {{#name}}, it treats name as a list/section: it looks the variable up in the current symbol table, then tries to descend into the list's item descriptors by reading that variable's list-descriptor pointer and building a fresh symbol-table scope from it — hashing each child descriptor's name string into a hash table, which requires taking the length of the name string, and that length call is where the fault surfaces.

The reproducer is the six-byte template "{{#readme ". In the fuzzer's descriptor table, readme is not a list at all — it is an ordinary escaped string variable. Because the list-descriptor pointer overlapped in the union with that string variable's second function pointer, reading it for readme did not yield a clean null ("this is not a list") value; it yielded the bytes of a genuine code-segment function address, reinterpreted as if it were a pointer to a descriptor table. The parser therefore walked that bogus "table," read a supposed child descriptor's name field out of unrelated code/data memory, and handed that wild, high-valued pointer to the string-hashing step. The string-length call then dereferenced the wild pointer and took a SEGV — a READ fault at a high address (the classic "dereference of a high value address"), not a write, and the out-of-bounds access is a stray wild-pointer dereference rather than a linear overrun growing past the end of any specific buffer. Inputs that never open a section (including null/empty inputs) never reach the misread, which matches the recorded differential: the vulnerable build exits nonzero (crash) while the fixed build exits cleanly.

The upstream fix reshapes the descriptor struct: it lifts the list-descriptor pointer out of the union and makes it a first-class, standalone member of the descriptor, placed next to the offset field, and removes it from the sequence sub-struct where it previously lived. Given its own dedicated storage, the list-descriptor pointer is now independent of the string and lambda payloads: for any variable that is not a sequence, the static initializers simply leave it null, so opening a non-list variable as a section now reads a null list descriptor and the parser rejects it cleanly (it returns a "no such device" error and aborts the section descent) instead of iterating a garbage table. Sequence variables continue to set the pointer explicitly, so legitimate list iteration is unchanged. The change is confined to the descriptor's header type definition, which lines up exactly with the reported failure: the crash is purely a consequence of the struct's memory layout (a union-aliased pointer read for the wrong variable kind), so correcting the layout in the header is the entire fix, and nothing in the parser or the hashing code itself needed to change.

The recorded fix commit modifies precisely the header that defines this descriptor union, moving the list-descriptor pointer out of it, and the crashing call path runs directly through the parser step that reads that pointer during section descent; the report metadata also marks this same commit as the verified fix for the testcase. The fix commit therefore looks correct. This is a distinct bug from the other shipped lwan finding (id 46506), which is a heap out-of-bounds READ in the HTTP/2 HPACK Huffman decoder's bit-consumption exhaustion check (an exact-zero boundary off-by-one causing one extra oversized lookahead load past a small heap buffer) — a different subsystem, source file, and fix entirely; the two share only the project.
