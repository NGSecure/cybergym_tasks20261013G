Project: jq (the command-line JSON processor). Fuzz target: jq_fuzz_execute, built with USE_DECNUM so numeric literals are handled by jq's bundled decNumber arbitrary-precision decimal library. Sanitizer: AddressSanitizer.

Crash: ASan reports a stack-buffer-overflow, WRITE of size 2, inside the decNumber library's low-level "copy a decNumber" routine, reached via the NaN-result helper (decNaNs) from decCompareOp / decNumberCompare, which are in turn called from jq's decimal number-comparison path while evaluating an inequality operator (the `!=` builtin) during program execution. The overflowed object is a small stack-local result decNumber (ASan names it `res`, a 12-byte frame slot spanning offsets [32,44)); the faulting write lands at offset 44, exactly 2 bytes (one decNumberUnit) past the end of that slot.

Mechanism (re-derived): The PoC drives jq to compare a decimal-literal value that is a NaN carrying a large diagnostic payload -- the classic trigger is an expression such as `1 != .` fed the input token `Nan4000`, i.e. a not-a-number whose payload digit string is long. When jq compares two number literals under USE_DECNUM, it declares a plain `decNumber res;` on the stack and passes it as the output operand to decNumberCompare(&res, a, b, context). A bare decNumber value is sized only for the default working precision: its coefficient-unit array (lsu[]) has just enough units for DECNUMDIGITS digits. That is fine for an ordinary numeric comparison result (which is a tiny -1/0/1 magnitude). But when either operand is a NaN, the comparison does not compute a numeric difference -- decCompareOp short-circuits into decNaNs, whose job is to produce a NaN *result* that propagates the operand's payload. decNaNs copies the source NaN (payload coefficient digits and all) into the caller-supplied result decNumber. Because the incoming NaN's payload has more coefficient digits than the default result buffer was sized for, copying its coefficient units writes past the end of `res`'s lsu[] array -- one extra decNumberUnit (2 bytes) beyond the 12-byte stack slot. Nothing bounds the copy to the declared capacity of the caller's result object, so an attacker-chosen NaN payload length directly controls how far the copy overruns.

Root cause: a fixed-size stack result buffer (a default-precision `decNumber`) is handed to a decNumber operation that, on the NaN path, copies an operand's full payload into it, without the caller reserving coefficient storage for a payload larger than the default precision. It is a genuine destination-side over-write driven by attacker-controlled payload length, not a read, not an off-by-one in unrelated arithmetic.

Direction: an out-of-bounds WRITE that grows forward (past the high end) of the stack-allocated result decNumber's coefficient-unit array `res`, overrunning it by one 2-byte decNumberUnit. The overflowed variable is the local comparison-result buffer; the data written is the copied NaN payload coefficient.

Fix (fix_files non-empty, patch examined): The upstream fix enlarges the result object at the call site of the number comparison. Instead of declaring a bare `decNumber res;`, the fixed code declares an anonymous struct that embeds a `decNumber` immediately followed by an extra `decNumberUnit units[1];`, and passes the address of the embedded decNumber to the comparison. This appends one additional coefficient unit of contiguous stack storage right after the decNumber, so the NaN-payload copy performed by decNaNs has room for the extra unit and no longer writes past the end of the stack frame. All references to the result are updated to reach through the embedded member. A regression test is also added that runs `1 != .` over a large-payload NaN under valgrind, and the security notes are updated to record this as CVE-2023-50268 ("fix stack-buffer-overflow if comparing nan with payload"). The patch changes no comparison logic; it only provides the missing destination capacity, which is exactly the precondition the overflow required.
