Project: dawn (Google's WebGPU implementation). The crash is reached through dawn's Tint shader component, whose SPIR-V reader validates every incoming SPIR-V binary with the bundled SPIRV-Tools validator (vendored under third_party/vulkan-deps/spirv-tools). Fuzz target: tint_spirv_tools_spv_writer_fuzzer. Feeding a crafted SPIR-V module to the parser makes Tint call SpirvTools::Validate() on it, and AddressSanitizer reports a heap-buffer-overflow with an 8-byte READ that lands exactly at the end (0 bytes to the right) of a 32-byte heap region. Thirty-two bytes is four 8-byte pointers: the region is a 4-element vector of basic-block pointers. The ASan allocation backtrace shows that buffer is the "postorder" list of basic blocks, filled one pointer at a time by a push_back inside a lambda in the validator's control-flow-graph check (PerformCfgChecks) while it runs a depth-first traversal over a function's CFG; the over-read itself happens afterward, inside the iterative dominator-computation helper that consumes that postorder list.

Mechanism: the dominator helper implements the classic Cooper/Harvey/Kennedy iterative algorithm. It numbers every block by its index in the postorder array and stores, per block, an immediate-dominator field that is a postorder index. That field is initialized to a sentinel meaning "not yet computed", and — this is the crux — the sentinel is chosen to be postorder.size() itself (i.e. one past the last valid index). The algorithm then iterates to a fixed point, and finally walks every block and emits a (block, dominator-block) pair by looking the dominator block up as postorder[dominator_field]. In a well-formed, fully reachable CFG every block's dominator field converges to a real index below postorder.size(), so this lookup is in bounds. But when a block's dominator field is never resolved and remains the sentinel, that final loop evaluates postorder[postorder.size()] — an index equal to the array length, i.e. one element past the end. With four blocks in the postorder array, that dereferences postorder[4] on a 4-element (32-byte) buffer, reading 8 bytes immediately to the right of it. That is precisely the "0 bytes to the right of a 32-byte region" READ-of-size-8 ASan caught.

Root cause: an unresolved dominator sentinel is used directly as an array subscript with no guard. The crafted module produces a function whose control flow leaves at least one block with an immediate dominator that the fixed-point iteration cannot pin down (a structurally disconnected / effectively-unreachable block, or one whose only predecessors themselves never obtain a defined dominator), so its dominator field is still the "undefined" sentinel — which equals the postorder length — when the emit loop indexes postorder with it. This is a logic/bounds defect in the validator, not memory corruption of the SPIR-V input: the incoming binary is untrusted attacker data, but the out-of-bounds access is on the validator's own internally-built postorder vector, driven by an unchecked sentinel index rather than by any length field taken from the input. This regressed with a mid-2022 SPIRV-Tools change that reworked how the CFG checker feeds blocks and predecessor relations into the dominator pass ("use structural dominance to validate cfg"), which made it possible for a block to reach the emit loop with an undefined dominator; it was a short-lived regression rather than a long-standing bug.

Direction: an out-of-bounds READ (not a write), of a single 8-byte pointer, one element past the high end (index == length) of the internally-built postorder vector of basic-block pointers. It is a sentinel-as-index over-read at the top of the array, not a negative index, not a forward over-read of an input/wire buffer, and not a write-side/destination overflow.

fix_commit judgment: the recorded fix_commit is a dawn commit, and inspecting it shows it changes only dawn's DEPS file — it rolls the third_party/vulkan-deps submodule pin forward and contains no source change in dawn's own tree. That is exactly why crash.json's fix_files is empty: the real code fix lives in the vulkan-deps/spirv-tools submodule that this roll pulls in, not in any dawn source file, and the vendored spirv-tools tree is not present in the provided source tarball (only dawn's first-party tree is), so the exact fixing spirv-tools commit cannot be diffed here. As a fix-boundary marker the roll is plausibly correct: its timing matches the OSS-Fuzz bisection window (the crash regressed on the build that first picked up the structural-dominance CFG rewrite and stopped reproducing one day later, when this roll landed), and a same-day submodule bump is the normal way such a validator fix reaches dawn. Two caveats keep this from being a clean file-level match: (1) it is a coarse dependency roll that can bundle unrelated submodule changes alongside the actual fix, and (2) the permanent, definitive guard for this exact out-of-bounds (skip the postorder lookup when the dominator field is still the undefined sentinel) was added to SPIRV-Tools only months later; the fix carried by this July roll was therefore a narrower correction to the block/predecessor feeding introduced by the regressing change, not that later guard. Net: fix_commit is consistent as the roll that crossed the fix boundary, but it is a submodule pin bump rather than the code fix itself, and empty fix_files is expected and correct for this vendored-dependency case.
