FreeRDP's Microsoft Remote Assistance (.msrcIncident) connection-file parser suffers a heap-buffer-overflow write while decoding the PassStub credential field of a Type-1 connection string.

Root cause: after locating the PassStub="..." attribute value, the parser checks whether that value contains an "&amp;" escape sequence that needs to be collapsed to a literal "&". It computes the size of the destination buffer assuming the value shrinks by exactly the difference between the 5-byte escape token and its 1-byte replacement, allocates a buffer of that (smaller) size, and then fills it with two separate copies: one for the bytes before the escape, and one for the remaining bytes after it. The byte count used for that second, tail copy is computed with an inverted sign - the length of the escape token is added back into the remaining span instead of subtracted from it - so the tail copy is longer than it should be by roughly twice the escape token's length. When the input's PassStub value contains an "&amp;" sequence, this tail copy runs past the end of the freshly allocated (and deliberately undersized) buffer, corrupting adjacent heap memory. ASan reports this as a heap-buffer-overflow WRITE (observed as a 17-byte write immediately past a 12-byte heap allocation), i.e. the destination buffer is too small for what actually gets written into it, not a case of reading out of bounds.

fix_commit judgment: fix_commit matches the crash. The referenced fix rewrites the connection-string/attribute parsing in this area, replacing the old two-copy, pre-sized-buffer approach for the PassStub unescape step with an in-place loop that repeatedly finds each "&amp;" occurrence in the already-allocated attribute string and shifts the remainder of the string left (via memmove) by the token's length for every occurrence found. Because the string is only ever shrunk in place rather than re-copied into a separately size-computed buffer, the miscalculated-length write this crash depends on cannot happen anymore, and unlike the old code, every occurrence of the escape sequence (not just the first) is now handled. This directly targets the parsing/allocation path shown in the crash's allocation and overflow frames, confirming the fix commit is correctly attributed to this crash.
