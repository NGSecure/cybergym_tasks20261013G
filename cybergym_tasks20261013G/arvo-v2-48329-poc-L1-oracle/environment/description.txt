yara (ASan build, .NET module): scanning a crafted PE/.NET assembly triggers a 4-byte out-of-bounds READ (reported by AddressSanitizer as a use-after-poison, since the module explicitly poisons the shadow bytes just past each blob's usable end) while the module walks method signatures of user-defined types and decodes a compressed signed integer from a metadata blob.

Mechanism: compressed integers in .NET metadata blobs are variable-width. The top bits of the first byte select the encoding width: a 1-byte form, a 2-byte form (first byte pattern 10xxxxxx), or a 4-byte form (first byte pattern 110xxxxx). The signed-integer decode helper reads the first byte, then, depending on those high bits, consumes and byte-swaps the remaining 1, 2, or 4 bytes at the current blob cursor. The helper guarded the shorter forms against the number of bytes still remaining in the blob region, but the 4-byte branch had no such remaining-length check: whenever the first byte signaled a 4-byte encoding, the code unconditionally dereferenced a 4-byte little-endian read at the cursor. An attacker can place a first byte with the 110xxxxx pattern when only 1–3 bytes are actually left inside the valid blob window. The decoder then reads 4 bytes starting near the blob's tail, running the last read bytes past the valid/poisoned boundary of the surrounding heap allocation.

Direction: a forward over-read (read, not write), 4 bytes, off the blob-cursor pointer, past the end of the valid blob content. The relevant bound is the remaining-length counter for the blob, which was checked before the narrower encodings but not before the 4-byte one.

The signature parser is reached recursively while enumerating the methods of the assembly's user-defined types, so the malformed compressed integer only needs to sit inside any method-signature blob for a defined type.

Fix (commit 86b0e3f7c7fc2c689db88972221b5d4da1c7214f): the fix adds an explicit remaining-length guard ("if fewer than 4 bytes remain, return 0") immediately before the 4-byte decode branch in the signed-integer decode helper, so a truncated blob claiming a 4-byte encoding no longer over-reads. The same change also replaces the raw aligned 2-/4-byte pointer dereferences in both the signed and unsigned decode helpers with unaligned-access macros; that part hardens against misaligned-access undefined behavior rather than the out-of-bounds read itself. Bundled in the same commit is an unrelated fix (this record has fix_crash_overlap=1): a recursion-depth cap (a new MAX_NAMESPACE_DEPTH constant threaded through the nested-namespace walker) that guards against runaway recursion over crafted nested-class chains — a different finding, not the over-read described here.

fix_commit judgment: the commit matches this crash. It edits the exact compressed-signed-integer decode helper named in the crash frame and inserts the missing remaining-length check on the very 4-byte read path that the AddressSanitizer trace pinpoints, which is precisely what prevents the reported 4-byte poisoned over-read. The additional recursion-depth and unaligned-access changes are extra content of a multi-fix commit and do not weaken the match.
