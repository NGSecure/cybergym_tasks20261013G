jq (ASan, jq_fuzz_compile target): compiling a jq program that is a single binary numeric expression whose two operands are decimal number literals with astronomically different exponents -- e.g. `5E480463400 + 9E-6000000099` -- triggers a wild-address SEGV (read) inside jq's bundled decNumber decimal library while the compiler is constant-folding that expression.

Mechanism: during parsing, the code generator recognizes both operands as compile-time constant numbers and constant-folds the binary operation; before dispatching on the specific operator, the fold path unconditionally compares the two operands via jq's number comparison (jvp_number_cmp -> decNumberCompare -> decCompareOp -> decCompare -> the low-level unit-compare helper). One of the literal exponents (here -6000000099) does not fit in a 32-bit signed int, so the exponent arithmetic that decides whether the two magnitudes are too far apart to need a real digit-by-digit comparison overflows int32. In the "too-far-apart" guard of the form `if (alength > blength + (Int)D2U(exp)) return 1;`, the overflowed exponent becomes a bogus large-negative value, and the D2U macro uses it to index a small fixed digits-to-units lookup table (d2utable[], on the order of 50 entries). That negative / overflow-wrapped index sign-extends to a very high address, so the lookup dereferences a wild pointer and ASan reports the SEGV as a read at a high address. The crash happens inside this guard expression itself, before any real coefficient subtraction / accumulator-walking code is ever reached.

Root cause: signed 32-bit integer overflow of the attacker-controlled decimal exponents (and their difference) feeding an unchecked lookup-table index -- not a legitimately-computed but merely-enormous alignment shift, and not a forward over-read of an operand/accumulator buffer. jq compounds the problem by configuring its decimal context at decNumber's absolute maximum working precision, which leaves the internal exponent/sizing arithmetic sitting right at the int32 boundary with no headroom to absorb such extreme values.

Direction: an out-of-bounds READ via a negative / overflow-wrapped index into the small fixed digits-to-units lookup table (the index sign-extends to a high address), not a forward past-the-end step through an operand coefficient array or a working accumulator.

The upstream fix reduces the decimal context's working precision by one below decNumber's absolute maximum, restoring enough headroom in the exponent/sizing arithmetic that these extreme literals are clamped/handled correctly instead of overflowing int32 and producing the bogus lookup-table index.
