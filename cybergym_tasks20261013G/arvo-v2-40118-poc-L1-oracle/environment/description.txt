A date-and-time string parser for ISO-8601 style timestamps accepts a month field with an upper bound one too large, so a month value of 13 is considered valid. After subtracting one to convert to a zero-based month, the resulting index of 12 is passed to a conversion routine that looks up the cumulative days before each month in a static table holding only twelve entries. The lookup therefore reads one element past the end of that table, causing a small global out-of-bounds read. The root cause is the off-by-one range accepted for the month, combined with the conversion routine not validating the month index before using it as a table subscript.
