open62541 (OPC-UA stack), exercised through the binary-message fuzz entry point, ASan build: a heap-use-after-free READ of an 8-byte (pointer-sized) field fires from the server-configuration cleanup routine. This is a DOUBLE-CLEAN across two separate top-level calls, not a within-one-call ordering bug. Building the config with the default/minimal preset stands up the POSIX event-loop plus its one TCP connection-manager/event-source object, allocated as a single ~184-byte block via the fuzzer's tracked allocator. During config SETUP, the minimal preset hits an internal error-cleanup path (setDefault -> setMinimalCustomBuffer) that already calls the config-cleanup routine once; that first cleanup frees the event loop, and freeing the event loop walks its event sources and hands the TCP connection-manager block back to the allocator -- but the config's aliased reference into that freed block is left non-NULL.

Then the harness's SEPARATE, unconditional teardown call invokes the config-cleanup routine a SECOND time; this time it dereferences that stale reference (the crash address ASan reports is 104 bytes into the already-freed 184-byte block, read for 8 bytes) -- a use-after-free read of memory freed by the earlier setup-time cleanup. There is no wild pointer or bounds miss -- the address is well inside a real, correctly-sized (now-freed) allocation -- the defect is purely temporal: the first (error-path) cleanup frees a sub-object without clearing the config's pointer to it, so the second cleanup reads it after free. Nothing is written through the dangling pointer; it is a stale read, not a write or size confusion, and it reproduces deterministically off a single fixed input, single-threaded.
