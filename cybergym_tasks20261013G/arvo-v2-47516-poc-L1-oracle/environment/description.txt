Dawn's Tint shader compiler, reached here through the SPIR-V reader fuzz target (a SPIR-V binary is parsed into Tint's AST and then handed to the resolver). Before the main semantic resolve runs, the resolver first builds a dependency graph by scanning every global declaration; that scan walks each function body, each statement, each type, and finally each expression tree to record which symbols the declaration refers to. Expression trees are walked by a small generic helper that does an iterative (non-recursive) traversal using a work-list: it keeps a std::vector of expression pointers still to visit, seeds it with the root expression, and then loops while the vector is non-empty. On each iteration it takes the last pending pointer, removes it from the back of the vector, invokes the per-node callback for it, and pushes that node's child expressions back onto the vector to be visited next.

The defect is in how the loop grabs that last pending pointer. It binds a *reference* that aliases the vector's back element, and then immediately pops the back element off the vector. Popping does not free the vector's backing buffer, but it does shrink the container's logical size, so the slot the reference still points at now lies in the region between the vector's new size() and its capacity() -- storage that is still allocated but no longer a live element of the container. Every subsequent use of that reference in the same iteration (dereferencing it to get the expression pointer and to switch on the node's kind) reads through an alias to an element that has already been removed. Under the AddressSanitizer build, libc++'s container-overflow annotations mark the between-size-and-capacity bytes as poisoned, so the very next read of the aliased 8-byte pointer is reported as an AddressSanitizer container-overflow READ of size 8; it is a stale-reference / use-after-pop bug (the commit calls it a use-after-free), where the "freed" memory is the just-popped tail slot of the work-list vector rather than a heap block returned to the allocator. Because essentially any non-trivial expression drives at least one pop-then-use cycle, the fault fires on almost every input that reaches the dependency scanner, which is why it was flagged as a frequent fuzz-blocker rather than a rare edge case.

Direction and root cause: the erroneous access is a READ, of a single pointer element, positioned just past the work-list vector's current logical end (in the [size, capacity) window created when the element was popped) -- i.e. reading the element that pop-back logically removed while a reference to it was still held. The root cause is retaining a reference into the work-list across the pop that removes the referenced element; the fix takes the back element by value (a copy of the pointer) before popping, so the loop body works with a stable copy that is unaffected by the container shrinking.
