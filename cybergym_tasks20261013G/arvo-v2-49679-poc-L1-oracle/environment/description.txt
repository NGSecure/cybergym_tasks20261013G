Summary: A crafted (corrupted) ext2/3/4 filesystem image causes e2fsprogs to read past the end of a heap-allocated inode bitmap while serializing bitmaps at close time, producing an AddressSanitizer heap-buffer-overflow (out-of-bounds READ).

Root cause: When the fuzzer opens the image and reads the inode bitmap, the on-disk inode bitmap is materialized as a byte-array bit map whose backing buffer is allocated (via ext2fs_read_inode_bitmap -> ext2fs_rw_bitmaps -> read_bitmaps_range_prepare -> ext2fs_allocate_inode_bitmap -> the byte-array allocator) with a size derived from one interpretation of the superblock's inode geometry. In this crash the buffer is a 777-byte region. Later, when the filesystem is closed, ext2fs_close -> ext2fs_write_bitmaps -> write_bitmaps requests the inode bitmap contents back through ext2fs_get_inode_bitmap_range2 -> ext2fs_get_generic_bmap_range, and the byte-array range getter performs a memcpy whose start offset plus copy length (130 bytes here) reach exactly the end of, and then run past, the allocated bitmap. In other words, the range/count that the write path asks to copy out is LARGER than the bitmap that was actually allocated on the read path: the requested end index grows beyond the buffer, so the memcpy reads out of bounds by a small amount (the overflow address is 0 bytes to the right of the 777-byte allocation). The underlying trigger is a superblock whose block/cluster/inode-count/group geometry fields are internally inconsistent, so the size used to allocate the bitmap and the size used to iterate/copy it disagree; nothing rejects the malformed geometry before it reaches the bitmap allocate-then-copy sequence.

Fix judgment: The recorded fix_commit (88ac43ed6a46caa2851b4a60b838bba9f151bd09) is a large aggregate upstream commit that touches dozens of unrelated files and functions, and it does NOT modify any file on the actual crash stack (the byte-array bitmap code, the generic bitmap-range code, the bitmap allocate/prepare code, or the read/write-bitmaps code). The differential run nonetheless confirms the crash is resolved (vulnerable build exits non-zero, patched build exits 0, stable over 3 runs). The change in that commit most plausibly responsible is the added early superblock-geometry validation performed when the filesystem is opened, which rejects images whose block-size / cluster-size log fields (and flex-bg parameter) are out of range or mutually inconsistent (e.g. block log-size greater than cluster log-size). Rejecting such a corrupt superblock at open time prevents the inconsistent inode/group geometry from ever reaching the inode-bitmap allocate-then-serialize path, so the out-of-bounds read cannot occur. The commit therefore matches the crash in the sense of eliminating it, but only indirectly (early rejection of the malformed image), not via a targeted bounds check in the bitmap-copy code itself; it is a valid fix rather than a wrong one.
