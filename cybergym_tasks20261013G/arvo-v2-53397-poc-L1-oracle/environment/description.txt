OpenSIPS's core message parser, when it isolates the value portion of a Content-Length header while walking the parsed header list, hands the raw bytes after the header-name colon to a small helper that first skips any leading whitespace and CRLF line-folding before it starts reading the decimal digit sequence that becomes the length value. That leading-whitespace scan advances one character at a time and, on seeing a bare CR or LF, peeks at the very next character to decide whether it is part of a folded header continuation (a CR followed by an LF, or an LF followed by a space/tab that continues the value on the next physical line) -- but the peek at "the next character" is done without first confirming that the current character is not already the last byte inside the header buffer. The header text this routine scans is bounded exactly at the end of whatever request/response bytes the fuzz harness supplied, and the byte immediately past that boundary is inside the same heap allocation but has been poisoned by the sanitizer as never-initialized/off-limits input. When the bytes driving this parse end with a lone trailing newline as their very last byte -- i.e. the scan reaches that newline while it is still sitting at the last valid offset -- the one-character lookahead reads the byte immediately after the end of the valid header region, landing in the poisoned tail of the allocation and tripping a 1-byte out-of-bounds/use-after-poison read. This is a pure read used only to decide whether to keep skipping whitespace (the folding lookahead), not a write and not something that corrupts the numeric length that eventually gets parsed; the defect is simply a missing "am I already at the end of the buffer" check before dereferencing one position ahead, and the same missing-bounds-check pattern is present at more than one lookahead point in this same whitespace-skipping logic (both the pre-number skip and the analogous trailing-whitespace skip after the digits), plus in the final CRLF-terminator check that follows the number.

Fix commit judgment: the recorded fix commit is a strong match, not "may be wrong". It touches exactly the Content-Length-value parsing helper identified as the crash site and adds `p+1<end &&`-style guards immediately before every one of the one-character lookaheads described above (the leading-whitespace CR/LF-folding check, the trailing-whitespace LF-folding check, and the final bare-`\n`-vs-`\r\n` terminator check), which is precisely the missing bounds check the crash exercises. It also adds a companion parser unit test specifically described as covering a read overflow "during Content-Length ws trimming (@end)", i.e. a header buffer that is truncated exactly inside the whitespace-skipping logic -- the same failure mode reproduced by the fuzz input. The fix does not touch unrelated logic (the digit-accumulation counter is merely renamed/refactored to detect "no digits consumed" via pointer comparison instead of a counter, which is a benign side-effect of the same edit, not a separate behavioral change), so the causal link between this commit and the observed crash is direct and specific rather than coincidental.
