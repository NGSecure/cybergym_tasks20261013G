uWebSockets' pub/sub topic tree, exercised through its publish/subscribe fuzz entry point (ASan build): the topic tree keeps every subscriber that still has buffered, undelivered messages threaded onto one intrusive doubly-linked list via prev/next pointers, with a single head pointer to the first such subscriber. When a subscriber is torn down (or otherwise removed) while it still needs its pending messages drained, the tree unlinks it from that list by patching its neighbors' prev/next pointers — but the head-pointer case is handled wrong: instead of advancing the head to the removed subscriber's next neighbor, the head is unconditionally reset to null whenever the subscriber being removed happens to currently be the head. If other subscribers remain further down the chain, that single reset detaches the rest of the list from all future traversal in one step, even though those remaining subscribers still believe they are staged for drainage and the tree's own message-retention bookkeeping still expects them to be reachable from the head. On a later publish/drain pass, the callback-invoking traversal ends up handed a reference to a message string that lives inside a std::vector<std::string> buffer whose backing storage has since been resized/reused elsewhere, because the accounting that should have kept that particular slot alive was itself driven by the now-broken list. The callback calls length()/size() on that stale string, and the one-byte read of the string's short/long-string discriminator lands just past what the vector's container-instrumentation still considers "live" for the reallocated buffer — an AddressSanitizer container-overflow, a 1-byte READ that stays inside the allocation's real memory but past the boundary the container's own shadow-byte bookkeeping tracks as valid, rather than an overrun into unmapped memory.

fix_commit 7a3bc47f753c192a54c11a3bfe826d1af8b92eda touches only the library's own header implementing this topic tree (not anything under the fuzzing/ harness directory), and it matches the crash precisely: the previously duplicated unlink-from-the-drainage-list logic — present at two separate call sites, one of them with an explicit comment noting it must "properly unlink" the subscriber, unlike a sibling code path that does not — is factored into one new private helper, and in doing so the head-pointer bug is corrected: the helper now sets the list head to the removed subscriber's *next* neighbor instead of unconditionally nulling it. Given this changes core product logic in the library's own subscriber-list bookkeeping and nothing in the fuzz driver, this is NOT the known uWebSockets harness-only family (the fuzz driver's on_connect_error/on_close missing a `client = nullptr` statement) — it is a genuine product bug, and the fix directly addresses the root cause of the crash rather than papering over harness misuse.

Direction: a 1-byte READ into a std::string's internal state (its short/long-string discriminator, touched via length()/size()), reached through a stale reference to a string that logically should still be pending delivery but whose backing vector storage had already moved/been reused — a lifetime/stale-reference bug (a linked-list head pointer prematurely nulled, silently detaching still-live subscribers from the drain-tracking structure) rather than a simple buffer that merely grew or shrank past its bound.
