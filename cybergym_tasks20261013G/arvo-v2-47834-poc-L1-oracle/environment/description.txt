Summary: grpc's client-side fuzz harness triggers a 1-byte heap-use-after-free read inside zlib's decompression state machine while grpc decompresses an incoming gRPC message whose "internally compressed" flag is set; AddressSanitizer reports the stale read happening deep inside zlib's own decode logic, reached through grpc's stream-message decompression helper, which in turn is invoked from the HTTP message-decompression filter's receive-message-ready path as soon as a message becomes available on the call.

Root cause: the freed object is one of the large slices that made up the connection's incoming byte buffer (originally allocated as a single big slice for the fuzzer-supplied input). In the vulnerable code, the receive-message-ready handler of the decompression filter did not pull/own the compressed message's bytes independently; it instead handed the decompression helper a slice buffer that still aliased storage owned and managed by the HTTP/2 transport's own read/parsing path. That transport read path unrefs and frees slices out of its incoming buffer once it believes it is done consuming them (as part of continuing to process the same connection's data), and in this trace that release happened before the decompression filter's callback actually finished reading through those same slices. The result is a straightforward buffer-lifetime/ownership mismatch — a use-after-free, not an out-of-bounds size bug — where zlib ends up dereferencing a slice pointer whose backing allocation was already released by an unrelated part of the transport.

fix_commit judgment: 713a1581d5c17a3445e6faa8262ec57b8743395a is consistent with this crash and very likely correct (not "may be wrong"). Its diff rewrites exactly the two sides implicated by the trace: (1) the HTTP message-decompression filter's receive-message-ready handling is restructured so it no longer grabs the shared slice buffer directly for a synchronous decompress call — it now walks the pending message stream and pulls each slice into a buffer the filter itself owns, only starting decompression once the whole message has been positively acquired that way; and (2) the same commit also touches the HTTP/2 transport's read/parsing code path and the lower-level slice-buffer/byte-stream lifetime primitives that back both sides of this hand-off. Because the fix directly changes both the freeing side (transport read path) and the use side (decompression filter) named in the crash's own call stack, rather than some unrelated area of the codebase, the match is direct rather than coincidental.
