This target is not a third-party Python package but CPython itself (the reference interpreter's parser and Unicode machinery), exercised through the python-library-fuzzers ast fuzz entry point, which feeds a crafted byte string straight into the built-in compile() so the PEG parser tokenizes and parses it as Python source. Under an AddressSanitizer build, ASan reports a heap-buffer-overflow READ of 1 byte, one byte past the end of a small heap allocation, while the interpreter is handling a self-documenting ("debug") f-string replacement field of the form f'{expr=}'. The defect lives in CPython 3.12's f-string tokenizing path: when the tokenizer opens a replacement field it allocates a heap buffer sized to exactly the remaining source text and copies that text in with strncpy (so the buffer holds no trailing NUL), recording the buffer length; a separate per-field "end offset" is only filled in later, when the field's closing '}', ':' or '!' is actually reached, and until then it retains its sentinel value of -1. When the parser subsequently builds the debug-text constant for such a field, it decodes that buffer as UTF-8 using a length computed as (buffer_length minus end_offset). If the source is malformed so that a debug field is opened but its closing delimiter is never tokenized before a syntax error occurs -- as with an input like f'{_=}{;' where a second replacement field begins with an illegal character -- the end offset is still the -1 sentinel, so the decode length evaluates to buffer_length minus (-1), i.e. buffer_length plus one. The UTF-8 decoding routine is therefore told the buffer is one byte longer than it really is and reads one byte beyond the (here two-byte) allocation: an out-of-bounds read just past the high/right end of the buffer, caused by an over-large length value rather than by any pointer-arithmetic mistake or a write. The upstream fix restructures the flow so the debug expression is decoded inside the tokenizer at the exact moment a legitimate closing delimiter is seen (which guarantees the end offset has already been assigned a valid, non-negative value), stores the decoded text on the token, and has the parser reuse that pre-decoded text instead of re-decoding the raw buffer with a possibly-uninitialized length -- closing the path where a still-open field could be decoded while its end offset was still the -1 sentinel.
